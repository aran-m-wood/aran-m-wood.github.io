Data Recovery, Hardware Rebuild, and Workstation Hardening on a Failed NVMe SSD

Nov 23, 2026 | Aaron M. Wood

System: MSI GS65 Stealth — Intel Core i7-9750H, 16 GB RAM, 512 GB NVMe SSD (failed; replaced with a 1 TB M.2 2280 NVMe), UEFI/GPT. OS: Windows 11 Home 24H2, recovered and rebuilt via Windows PE.

After a boot loop and a failed Windows Recovery Environment (WinRE), I recovered the user data from the non-booting drive, replaced the failed SSD, and rebuilt the OS on a hardened baseline before restoring any data. Working from Windows PE boot media, I bypassed the corrupted boot chain, rebuilt an external backup drive as NTFS, and copied 166.75 GB (28,758 files) with multi-threaded robocopy; then I identified a drive that had stopped accepting writes, replaced it through a full chassis teardown, and provisioned a clean install with pre-boot full-disk encryption, encrypted DNS, and segmented browsers.

Scope, stated honestly: this was offline recovery from a drive that was still readable, not live acquisition from a running system, and I did not maintain a forensic chain of custody. The integrity check here is a transfer-log audit, not a cryptographic hash comparison. Those limits are noted where they apply.

Phase 1 — UEFI/BIOS triage and WinPE shell

Standard boot looped into the BIOS, and the built-in WinRE triggered hardware resets, so I moved to an external environment. I audited the UEFI boot configuration and booted directly from external Windows 11 24H2 installation media via the hardware boot menu. At the installer's partition-selection screen I opened an elevated command prompt (Shift + F10) with raw block-device access, rather than running the GUI installer.

Phase 2 — Boot-record and filesystem checks

Before changing anything on disk, I separated logical corruption from physical failure. I ran bootrec /scanos, bootrec /rebuildbcd, and bootrec /fixmbr. bootrec /fixboot returned Access is denied, and /scanos found 0 Windows installations. On a UEFI/GPT system the boot files live on the FAT32 EFI System Partition, not in a legacy MBR boot sector, so /fixmbr and /fixboot are not the right repair here — bcdboot against the EFI partition is (see "What I'd do differently"). I enumerated logical disks with wmic logicaldisk and confirmed the primary NTFS user directory was readable, which meant the data could be copied before any repair.

Phase 3 — External storage and data copy

Initial backup staging to a 1 TB external drive halted at 29.08 GB: the drive carried a legacy ~32 GB FAT32 partition that left ~900 GB unallocated and imposed a 4 GB single-file limit. I rebuilt it:

  • Clear: diskpart → list disk → clean isolated the 931 GB external target and removed the legacy FAT32 layout.
  • Provision: create partition primary → format fs=ntfs quick gave one 931 GB NTFS volume able to hold large files and ACL metadata.
  • Copy: robocopy [src] [dst] /E /XJ /XD "AppData" /R:1 /W:1 /MT:8 — multi-threaded, one retry per file, skipping junctions and the transient AppData cache.

The copy moved 166.75 GB — 28,758 files across 7,338 directories — in 32 minutes, about 87 MB/s average. The two logged errors (389.8 KB, ERROR 1920) were offline OneDrive cloud-only placeholder files, not local corruption; I confirmed that rather than assuming it. One honest limit: this verifies the copy completed and accounts for every error, but it does not prove the files are bit-identical, because I did not hash them before and after. [Confidence: copy complete — High; copy bit-identical — unverified.]

Phase 4 — NVMe fault isolation and hardware fix

With the backup verified complete and the external drive disconnected, I tried to wipe the internal 512 GB NVMe for a clean install. attributes disk reported Current Read-only State: No, and I dismounted the active OS/recovery volumes (remove all dismount). clean still returned Access is denied, and on reboot the disk reverted to its previous state — every write was lost. That behavior is consistent with a controller-level write-lock. [Confidence: Medium — based on the drive's behavior through diskpart, not on SMART/health data, which I could not read off the failing controller.]

I then disassembled the GS65 chassis, disconnected the battery and ribbon assemblies, removed the failed M.2 SSD, installed a 1 TB M.2 2280 NVMe, and renewed the CPU/GPU thermal paste while the board was out.

Phase 5 — Clean OS and host hardening

I enforced every control below before reconnecting the backup drive, so recovered data never touched an unhardened system.

  • Telemetry and cloud decoupling: disabled advertising ID, optional diagnostic telemetry, activity history, cloud search indexing, and lock-screen/Start suggestions; removed OneDrive; disabled Fast Startup so session and key material isn't persisted in hiberfil.sys.
  • Pre-boot full-disk encryption: VeraCrypt system encryption (AES / SHA-512, hardware-accelerated via AES-NI) with a strong pre-boot passphrase and a rescue disk kept on external media; confirmed 100% encryption before writing any recovered data.
  • Encrypted DNS and network posture: set the network profile to Public (blocking SMB sharing and LAN discovery) and enforced system-wide DNS-over-HTTPS via Quad9, verified against Quad9's check page.
  • Segmented browsers: Brave for signed-in work (hardened shields, V8 JIT disabled, WebRTC non-proxied UDP disabled, Quad9 DoH); LibreWolf for research (strict anti-fingerprinting, uBlock Origin, HTTPS-only, Multi-Account Containers); Tor Browser for unattributed clearnet lookups only — no logins, downloads, or .onion access from this workstation.
  • Host vs. lab separation: a dedicated, isolated directory for forensic artifacts and VM disks, kept off the host's normal profile, with a strict rule against running untrusted binaries on the host — anything to be detonated runs only inside an isolated VM.

What I'd do differently

  • Back up before any repair. I ran bootrec before finishing the backup. On a readable but non-booting drive the correct order is copy first, repair second — a repair that writes to disk can make a marginal drive worse.
  • Use the right UEFI repair. bootrec /fixmbr and /fixboot target legacy MBR; on UEFI/GPT the repair is bcdboot C:\Windows /s <EFI>: /f UEFI.
  • Hash before and after. Without pre/post hashes I can say the copy finished, not that it's identical; a Get-FileHash manifest on both sides would make the integrity claim real.
  • Capture drive health earlier. The write-lock diagnosis is Medium confidence for lack of SMART data; reading the failed drive in a USB M.2 enclosure (CrystalDiskInfo / smartctl) could raise it to High.

Skills demonstrated

Data recovery from a non-booting system, WinPE/WinRE triage, UEFI/GPT and NVMe diagnostics, diskpart and robocopy; laptop teardown, M.2 NVMe replacement, thermal service; VeraCrypt pre-boot full-disk encryption, DNS-over-HTTPS (Quad9), browser attack-surface reduction, and host/VM isolation.
